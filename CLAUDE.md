# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

HydroMonitor: a water quality monitoring system. A single ESP32 board reads DS18B20 temperature, analog turbidity, and TDS (dissolved solids) sensors and POSTs readings to a backend, which relays them to a live browser dashboard. There is no camera/image-based inference in this project (an earlier ESP32-CAM + Roboflow YOLO pipeline was removed).

**`main.py`** (FastAPI) is the one and only backend — referenced by `webconfig.json` and the ESP32 firmware's `backendPort`. It handles HTTP sensor ingestion, WebSocket UI broadcast, local SQLite persistence (`storage.py`), and UDP-based backend discovery for the firmware. (An earlier alternative Node `ws` relay, `server.js`, no longer exists in the tree; `ws_client.py` is a small standalone WebSocket test client, not a second backend.)

Firmware source lives in this repo at `firmware/esp32/esp32.ino` (moved here from the standalone Arduino sketches folder for consolidation). To edit/compile it in the Arduino IDE, open the `.ino` directly — the containing folder name matches the sketch name, which the IDE requires.

## Running

```
pip install -r requirements.txt
python main.py
```
Serves on `0.0.0.0:8080`. The default page (`frontend/`, see Frontend below) must be built first: `cd frontend && npm install && npm run build`, which produces `frontend/dist/`, mounted at `/`. A WebGL build directory (default `Build/`, configurable via `webconfig.json`'s `staticDir`) is mounted at `/{staticDir}` with Brotli/gzip content-encoding support for precompressed assets — unrelated legacy Unity output, not part of the dashboard.

**Autoreload is opt-in via `HYDRO_DEV=1`** (`python main.py` alone runs with `reload=False`). Do not re-enable it by default: the reloader watches the working directory, so every calibration save (writes `calibration.json`) and every history write (`history.db`) would restart the server, dropping all dashboard WebSockets and wiping `history_buffer`/`sensor_stats`.

**Deployment**: `scripts/install-service.ps1` installs `main.py` as a Windows service via NSSM (restart-on-failure, rotated logs in `logs/`, `AppDirectory` set to the repo root — `main.py` resolves `webconfig.json`, `calibration.json`, `history.db`, and `frontend/dist` relative to cwd). Run it from an elevated prompt; `-Uninstall` removes the service. Without it the deployment is a terminal window, and a reboot silently ends monitoring.

There is no test suite or linter configured for the backend; the frontend has `npm run lint` (oxlint) and `npm run build`.

## Architecture (main.py / FastAPI path)

- **Config**: `webconfig.json` sets `staticDir` (WebGL build output folder), `googleSheetsWebhookUrl`, `calibrationFile`, `historyDbFile` (local SQLite history; `""` disables it, default `history.db`), and `historyRetentionDays` (pruned once at startup; `0` keeps everything, default 365). Missing file/keys fall back to those defaults.
- **Sensor ingestion** — `POST /update`: accepts either JSON body (`{temperature, turbidity, tdsVoltage}` from current firmware, or legacy `{temperature, turbidity, tds}`) or form-urlencoded body with `water_level`. Normalizes into a payload with `source`/`timestamp`, derives `ec` (electrical conductivity, µS/cm) from `tds` (`ppm_to_ec` — EC is not a separate sensor, it's the same DFRobot measurement before the standard EC→TDS ×0.5 conversion, so it always agrees with TDS), appends to the in-memory `history_buffer` for the live short-window graph, and broadcasts to all connected UI WebSocket clients as a `sensor_update` message. See Sensor calibration below for how `turbidity`/`tds` get calibrated before broadcast.
- **Dashboard fan-out** — `WS /ws/app`: browser dashboards connect here and receive `sensor_update` JSON messages. Connected clients are tracked in the `ui_clients` set guarded by `ui_clients_lock`; disconnects are pruned opportunistically during broadcast.
- **Backend discovery** — a UDP listener (`DiscoveryProtocol`, started via `@app.on_event("startup")`) binds `0.0.0.0:8888` and replies `HYDRO_HERE` to any `HYDRO_DISCOVER` packet, so firmware on the LAN can find this machine's current IP without it being hardcoded. Requires Windows Firewall to allow inbound UDP on port 8888 (added locally via `netsh advfirewall firewall add rule name="HydroMonitor UDP Discovery" dir=in action=allow protocol=UDP localport=8888` — a fresh machine won't have this rule and discovery will silently time out until it's added).
- **Push notifications** — on every `/update`, `_check_breaches_and_dispatch` inline-computes a per-param good→warn/danger *edge* (tracked in-memory in `last_severity`, so only the transition into a worse band fires, not every reading while it stays there), then dispatches fire-and-forget (`asyncio.create_task`) via Web Push (`pywebpush`) to every subscribed browser whose stored per-param/severity prefs opt in. Routes: `GET /push/vapid-public-key`, `POST /push/subscribe`/`/unsubscribe`, `GET`/`PUT /push/preferences` — all 503 when `storage.py` (which holds the subscriptions) is disabled. VAPID keys come from `webconfig.json` (`vapidPrivateKeyFile`/`vapidPublicKey`/`vapidSubject`); push silently no-ops without them (`vapid_available()`). Web Push requires a secure context, so `main.py` can also stand up an optional HTTPS listener (`httpsCertFile`/`httpsKeyFile`/`httpsPort`, default 8443) alongside the always-on HTTP:8080 that the ESP32 keeps using — without a cert/key configured, push only works when the dashboard itself is loaded over `localhost`. Breach thresholds live in `thresholds.py`, a **hand-mirrored duplicate** of the frontend's `lib/thresholds.ts` `RANGE_BANDS` (its own docstring says so) — nothing enforces the two staying in sync, so a frontend threshold/band edit needs a matching edit here.

## Sensor calibration (backend-owned)

Calibration lives on the backend, not the firmware, so sensors can be recalibrated live with **no reflash**. The firmware streams raw values; `main.py` converts them using coefficients persisted in `calibration.json` (path configurable via `webconfig.json`'s `calibrationFile`, default `calibration.json`; the file is git-ignored and created on first save). Missing/invalid file → sensible defaults (turbidity uncalibrated, TDS k-factor 1.0).

- **Models**: turbidity is a **2-point linear** ADC→NTU map (`ntu = slope·adc + intercept`; slope is negative since higher ADC = clearer water; needs ≥2 captured points or it returns `None`/no NTU). TDS is the DFRobot temperature-compensated ppm polynomial (moved here from the firmware, using the live DS18B20 temp) scaled by a **single k-factor** fitted against one known-ppm solution.
- **Calibration mode gate**: saved coefficients only apply when `calibration_mode` is ON (the `/calibrate` page's on/off toggle, `POST /calibration/mode`). OFF → `/update` always emits raw ADC (`turbidityUnit: "ADC"`) and uncalibrated DFRobot ppm (k=1.0), regardless of what's saved in `calibration.json` — so a saved-but-unverified calibration can't silently affect the live dashboards until explicitly switched on.
- **`/update` output**: emits both raw and calibrated fields. `turbidity` carries **calibrated NTU** once a calibration exists, else falls back to raw ADC — kept this way because the *original* React SPA that used to live at `/` was a prebuilt bundle we couldn't edit and hardcoded the "NTU" label on whatever `turbidity` contained (see Frontend below — that bundle is gone now, but the field shape stayed since the current frontend also just wants real NTU). `turbidityRaw` always carries the raw ADC (used by the calibration page and Google Sheets logging), `turbidityUnit` is `"NTU"`/`"ADC"` (the frontend reads it to label correctly), `turbidityNtu` is the calibrated NTU or `null`. TDS: `tdsVoltage` (raw) and `tds` (calibrated ppm).
- **Calibration page** — `GET /calibrate` serves `web/calibrate.html`, a self-contained standalone page (independent of the main frontend's own Calibration tab — see Frontend) that polls `GET /calibration` ~1s for live raw values, lets you enter a known reference + capture a point (the backend averages the last ~5 raw readings to reduce noise), shows the computed coefficients, and saves. Tracks an observed min/max of the live raw reading while turbidity is open (client-side only) with "use min"/"use max" buttons to fill the raw-ADC input, plus a "Reset range" button that only clears that local tracking, never the saved calibration.
- **REST API** (all under `/calibration*`, distinct from the `/calibrate` page): `GET /calibration` (state + `latestRaw`), `POST /calibration/mode` `{enabled}`, `POST /calibration/capture` `{sensor, reference, label?}`, `DELETE /calibration/point` `{sensor, index}`, `POST /calibration/save` (persists to `calibration.json`), `POST /calibration/reset` `{sensor}`. Captures/edits are in-memory until an explicit save.
- **Note**: Google Sheets logging is unchanged — it still logs raw ADC turbidity + (now backend-calibrated) TDS ppm. Adding NTU columns would require an Apps Script schema change.

## Google Sheets logging & history (`google_apps_script.gs`)

- Every `/update` POST that includes `temperature`+`turbidity` is relayed fire-and-forget (via `asyncio.to_thread`, so a slow/unreachable Google endpoint never blocks the ESP32's `/update` response) to a Google Apps Script Web App, configured by `webconfig.json`'s `googleSheetsWebhookUrl`. If that key is empty/missing, the relay and `/history` both no-op.
- `google_apps_script.gs` is reference-only — it does not run from this repo. Paste it into the target spreadsheet's **Extensions > Apps Script** editor and deploy as a Web App (**Execute as: Me**, **Who has access: Anyone**).
- **`doPost` inserts each new reading at row 2** (right after the header), pushing everything else down — newest reading is always the top data row. This was changed from the original bottom-append model so recent data is always readable without scrolling; older rows appended under the previous model just sit further down and are never touched. Columns: `Timestamp, Temperature (C), Turbidity (raw ADC), TDS (ppm)`. Turbidity is logged as the same raw averaged ADC value shown on the dashboard — the NTU conversion (`adc_to_ntu` in `main.py`) is currently bypassed pending calibration, so no calibrated NTU value reaches the sheet.
- `doGet` accepts `?seconds=` and `?maxPoints=` (default 900s / 400 points), reads a **leading** slice of the sheet (rows 2..N — the newest readings, matching the insert-at-top write above), reverses it back to chronological ascending order, filters to the requested window, and stride-downsamples to at most `maxPoints` so long windows stay small and fast.
- **`GET /history?window=`** — dashboard-facing endpoint in `main.py`, selectable window (`5m`/`15m`/`1h`/`3h`/`12h`/`24h`, default `15m`, `HISTORY_WINDOWS`). **Three tiers, cheapest first**, merged into one chronological list; the response's `source` field reports which contributed (e.g. `db`, `db+sheet`, `live`):
  1. **local SQLite** (`storage.py`) — answers any window straight off disk and survives restarts, so it is preferred whenever enabled;
  2. **in-memory `history_buffer`** — only contributes rows newer than the DB's newest (a failed insert), or everything when the DB is disabled;
  3. **Google Sheets** — proxies `doGet` with matching `seconds`/`maxPoints` (keeping the dashboard's fetch same-origin, avoiding browser CORS/redirect issues with Google), consulted *only* for the part of the window local sources don't reach: a fresh DB, a restored machine, or readings predating the DB.

  The gap test allows `HISTORY_GAP_TOLERANCE_MS` (15s) of slack — readings arrive every 2s, so the first row at/after a cutoff is essentially always a second or two late, and testing for an exact match made every steady-state request look like a gap and fire a pointless multi-second Sheets round-trip. Every row gets `turbidityNtu` (calibrated from raw ADC via `_with_ntu`) and `ec` (from `tds` if not already present) added uniformly across all three sources.
- **Local history database** (`storage.py`, `historyDbFile`) — every `/update` reading is written to SQLite (WAL, `synchronous=NORMAL`) via `asyncio.to_thread`, fire-and-forget like the Sheets relay, so disk latency never delays the ESP32's response. Column names deliberately mirror `history_buffer` and the Apps Script's `doGet` (`timestamp` in epoch **milliseconds**, `turbidity` = raw ADC) so rows from all three sources merge without translation. Failures here are never fatal — a bad path or permission error just logs and degrades to the previous buffer + Sheets behavior. The file is git-ignored (site measurement data, not code); back it up separately.
- **Redeploy gotcha**: after editing `doGet`/`doPost` in the Apps Script editor, redeploy the web app as a **new version** — otherwise `/exec` keeps serving the old code and `GET` silently returns nothing. The insert-at-top change described above lives only in this repo's reference copy until you do this; the currently-deployed script keeps appending at the bottom (still fully correct for `/history`, just not "newest at the top" if you open the sheet by hand) until redeployed.
- Running min/max per sensor (`temperature`/`turbidity`/`tds`) is tracked separately in `main.py`'s in-memory `sensor_stats` (since server start, resets on restart, shared across all connected dashboards) — it is not persisted to or read from the spreadsheet.

## Frontend

**One dashboard**, source-controlled, served at `/` by `main.py` (the built `frontend/dist/`, mounted last as a root catch-all — see `main.py`'s bottom `app.mount("/", ...)`, registered after every API route so it only handles requests nothing more specific already matched). Full design/build history is in **`AQUA_MONITOR_PLAN.md`** and **`HANDOFF.md`**; this section is the short version.

- **Stack**: Vite + React 19 + TypeScript + Tailwind v4, shadcn/ui + Recharts + Motion + TanStack Query. Build with `cd frontend && npm install && npm run build` (`tsc -b && vite build`, outputs `frontend/dist/`, git-ignored along with `node_modules/`); `/` 404s until this has been built at least once. `npm run dev` runs a Vite dev server that proxies `/ws/app`, `/history`, `/calibration*`, `/update` to `:8080` for HMR against a live `python main.py`. `npm run lint` runs oxlint. No test suite.
- **App shell** (`App.tsx`): `SensorProvider` (the one shared `/ws/app` socket, see Live data below) wraps `TabTitleSync` (sets the browser tab title to "Aqua Monitor — Connected"/"— Offline" off live WS state, deliberately always in English — a tab title is glanced at, not read) and `TourProvider`/`TourOverlay` (`components/tour/`, a guided onboarding tour that auto-starts once per browser via a versioned localStorage flag and is replayable via the sidebar's help-icon `TourHelpButton`), which wrap the actual layout: `AnimatedBackground` (a fixed full-viewport `<canvas>` behind everything — a slow wavy dot grid in the theme's `--primary`/`--accent` colors fading to `--background` at the edges via a radial vignette; pauses its `requestAnimationFrame` loop when the tab is hidden and skips animating entirely under `prefers-reduced-motion`), the nav rail, the routed view, and `RightContextColumn`.
- **Left nav — one collapsible rail, not two panels**: `RailHoverPanel` renders exactly one `Sidebar` and flips its `collapsed` prop on hover/focus (mouse/trackpad) or a global Spacebar keydown (ignored while a form field has focus) — the rail's own width/label transition (in `Sidebar.tsx`) is what makes it read as the same rail smoothly growing in place. (A second, full-width `Sidebar` sliding over the collapsed one as a separate overlay was tried and dropped — two unrelated DOM subtrees can't animate as one, it read as a panel awkwardly appearing over the rail.) Hidden entirely on phone widths in favor of `MobileTopBar`'s hamburger `Sheet` + `MobileBottomNav`.
- Three tabs — **Dashboard** (WQI history chart with a time-range selector and reference lines; a 2×2 live param grid for Temperature/Turbidity/TDS/EC with 30s sparklines; clicking any card opens a detail modal with a bigger chart, min/avg/max, a two-sided too-high/too-low warning, and — for TDS/EC — the spelled-out name under the acronym title via `ParamMeta.fullNameKey`; 3 radial safety gauges; a `QuickViewSummary` card in the right column, see below), **Calibration** (turbidity 2-point + TDS k-factor wired to the real `/calibration*` API, optimistic apply + toast, observed-range min/max/reset — see Sensor calibration above), **History** (`/history` table + CSV export) — plus a light/dark theme toggle, an EN/ไทย language switcher (all UI text centralized in `frontend/src/lib/strings.ts`), and a bell-icon `NotificationSettings` dialog (subscribe/unsubscribe + per-param warn/danger push prefs — breach detection itself is server-side, see main.py's Push notifications above).
- **QuickView summary** (`components/shell/QuickViewSummary.tsx`, dashboard-only): a compact WQI badge plus one row per param and a bilingual one-line analysis sentence, e.g. *"Check the sensors: TDS, EC may be disconnected. Moderate — watch: Turbidity."* Faulting params are named separately from merely out-of-range ones, since a faulting param's apparent "danger" status is itself a false signal from the fault, not a real reading about the water.
- **Sensor-fault detection** (`isSensorFault`/`RANGE_BANDS[param].sensorFaultBelow` in `lib/thresholds.ts`): flags any of the 4 params reading implausibly near zero — a disconnected DS18B20 reads exactly 0.0°C, a disconnected TDS probe reads ~0V → 0 ppm → 0 µS/cm — as a likely sensor fault rather than a genuine reading. Surfaced in `ParamGrid`'s card hint, the detail modal's `RangeWarning`, and QuickView's rows. **Hand-mirrored on the backend** in `thresholds.py` for push-breach detection (see main.py's Push notifications above) — the two must be kept in sync manually.
- **Live data**: `frontend/src/lib/useSensorSocket.ts` holds the one shared `/ws/app` connection (via `SensorProvider`) and a ~30s rolling per-parameter sample buffer for the sparklines, seeded from `GET /history?window=5m` on mount so a page reload shows recent data immediately instead of a blank chart that only refills as new readings trickle in. **No fake-data fallback**: on disconnect or >5s of silence it flips a `connected`/"Offline" flag but leaves the last real reading on screen, frozen — it never fabricates plausible-looking numbers. (An earlier version randomly generated readings when idle, mirroring the old vanilla dashboard's demo behavior; removed once the full ESP32 → backend → Sheets → frontend chain was wired to real hardware, since synthetic noise during a real outage is actively misleading for a monitoring system.)
- Two earlier dashboards were **removed** and neither their files nor their routes exist any more: a black-box prebuilt React SPA (`web-react/`, generated externally, could not be edited) that used to be served at `/`, and a hand-built vanilla dashboard (`web/index.html`+`app.js`+`style.css`) at `/classic`. Do not add code paths or comments referring to either; `web/calibrate.html` (see Sensor calibration above) is the one survivor from `web/`, kept as a lightweight standalone alternative to the main app's Calibration tab.

## Firmware (`firmware/esp32/esp32.ino`)

Single ESP32 dev board (not ESP32-CAM — no camera). Hardcodes Wi-Fi credentials. Not auto-synced with `main.py`; changing an endpoint contract there requires a matching firmware update.

Reads DS18B20 temperature, analog turbidity, and TDS every 2s and POSTs JSON `{temperature, turbidity, tdsVoltage}` to `http://<backendIP>:8080/update` — **all raw**: `turbidity` is the averaged raw ADC and `tdsVoltage` is the raw TDS sensor voltage. The DFRobot TDS ppm formula, its temperature compensation, and turbidity NTU conversion all now live on the **backend** (see Sensor calibration below), so the firmware no longer computes ppm — this lets sensors be recalibrated live without reflashing. (Older firmware that POSTs a pre-computed `tds` ppm still works: the backend passes it through unchanged.) The backend IP is not hardcoded: `discoverBackend()` broadcasts `HYDRO_DISCOVER` over UDP on port 8888 and takes the replying host's IP as the backend address, so it survives the backend PC's DHCP lease changing. Discovery runs once at boot (blocking retry loop) and again automatically if `/update` POSTs fail 3 times in a row (`consecutiveFailures` / `backendKnown`), so a mid-run IP change self-heals within a few broadcast cycles. Requires `main.py`'s discovery listener (see above) and a working Wi-Fi broadcast domain. Registers mDNS as `hydromonitor.local` but doesn't actually use that hostname anywhere — that's unrelated leftover, not part of backend discovery.

### Wiring

The turbidity NTU formula (`-1120.4·V² + 5742.3·V - 4353.8`) is calibrated for a 5V-powered analog turbidity sensor with a ~0–4.5V output range (DFRobot Gravity-style). ESP32 GPIOs are strictly 3.3V (not 5V-tolerant like some ESP8266 boards), so the sensor's output is scaled down through a voltage divider before reaching the ADC pin, and the firmware scales it back up (`dividerRecoveryFactor`) before applying the NTU formula.

| Sensor | Pin | ESP32 pin | Notes |
|---|---|---|---|
| DS18B20 (temp) | VCC | 3.3V | Keeps the OneWire data line's HIGH level at a safe 3.3V |
| | GND | GND | |
| | DATA | GPIO13 | Needs a 4.7kΩ pull-up to 3.3V (skip if the probe already has one). **Not GPIO12** — that's a boot-strapping pin (sets flash voltage); the required pull-up would hold it HIGH at reset and can prevent the board booting at all |
| Turbidity sensor | VCC | 5V / VIN | Needs 5V to hit its rated output curve — must be a true 5V rail |
| | GND | GND (shared) | |
| | OUT | → divider → GPIO34 | GPIO34 is ADC1 (input-only, no internal pulls); avoid ADC2 pins (0,2,12–15,25–27) since Wi-Fi disables ADC2 |
| TDS Meter V1.0 | VCC | 3.3V | Accepts 3.3–5.5V; output voltage is independent of supply choice |
| | GND | GND (shared) | |
| | A (signal) | GPIO35 (direct, no divider) | Output tops out at ~2.3V, safely under the 3.3V ADC limit. Another ADC1 pin, kept separate from GPIO34/GPIO13 |

Divider (turbidity only): R1 = 10kΩ (sensor OUT → node), R2 = 20kΩ (node → GND), node → GPIO34. Scales 0–4.5V down to 0–3.0V (safe margin under the 3.3V ADC limit); firmware multiplies by 1.5 (`dividerRecoveryFactor`) to recover the sensor's real voltage. Re-verify the NTU calibration against known reference samples once wired — the formula was tuned for the original ESP8266 read path, not this divider, and ESP32's ADC has known non-linearity near its extremes.

TDS reading uses DFRobot's official temperature-compensated formula, reusing the DS18B20's `temperatureC` (compensation coefficient `1 + 0.02·(T-25)`) rather than assuming a fixed 25°C, since the sensor's raw output drifts with water temperature.
