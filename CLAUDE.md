# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

HydroMonitor: a water quality monitoring system. A single ESP32 board reads DS18B20 temperature, analog turbidity, TDS (dissolved solids), and flow-sensor pulses, and POSTs readings to a backend, which relays them to a live browser dashboard (and, for threshold breaches, to subscribed browsers as OS push notifications — see Push notifications below). There is no camera/image-based inference in this project (an earlier ESP32-CAM + Roboflow YOLO pipeline was removed).

**`main.py`** (FastAPI) is the one and only backend — referenced by `webconfig.json` and the ESP32 firmware's `backendPort`. It handles HTTP sensor ingestion, WebSocket UI broadcast, local SQLite persistence (`storage.py`), and UDP-based backend discovery for the firmware. (An earlier alternative Node `ws` relay, `server.js`, no longer exists in the tree; `ws_client.py` is a small standalone WebSocket test client, not a second backend.)

Firmware source lives in this repo at `firmware/esp32/esp32.ino` (moved here from the standalone Arduino sketches folder for consolidation). To edit/compile it in the Arduino IDE, open the `.ino` directly — the containing folder name matches the sketch name, which the IDE requires.

## Running

```
pip install -r requirements.txt
python main.py
```
Serves on `0.0.0.0:8080` (plain HTTP, always on — the ESP32 firmware POSTs here). A second HTTPS listener on `0.0.0.0:8443` starts additionally when `webconfig.json`'s `httpsCertFile`/`httpsKeyFile` are set (see Push notifications below — Web Push needs a secure context for anything other than `localhost`). The default page (`frontend/`, see Frontend below) must be built first: `cd frontend && npm install && npm run build`, which produces `frontend/dist/`, mounted at `/`. A WebGL build directory (default `Build/`, configurable via `webconfig.json`'s `staticDir`) is mounted at `/{staticDir}` with Brotli/gzip content-encoding support for precompressed assets — unrelated legacy Unity output, not part of the dashboard.

**Autoreload is opt-in via `HYDRO_DEV=1`** (`python main.py` alone runs with `reload=False`). Do not re-enable it by default: the reloader watches the working directory, so every calibration save (writes `calibration.json`) and every history write (`history.db`) would restart the server, dropping all dashboard WebSockets and wiping `history_buffer`/`sensor_stats`.

**Deployment**: `scripts/install-service.ps1` installs `main.py` as a Windows service via NSSM (restart-on-failure, rotated logs in `logs/`, `AppDirectory` set to the repo root — `main.py` resolves `webconfig.json`, `calibration.json`, `history.db`, and `frontend/dist` relative to cwd). Run it from an elevated prompt; `-Uninstall` removes the service. Without it the deployment is a terminal window, and a reboot silently ends monitoring.

There is no test suite or linter configured for the backend; the frontend has `npm run lint` (oxlint) and `npm run build`.

## Architecture (main.py / FastAPI path)

- **Config**: `webconfig.json` sets `staticDir` (WebGL build output folder), `googleSheetsWebhookUrl`, `calibrationFile`, `historyDbFile` (local SQLite history; `""` disables it, default `history.db`), and `historyRetentionDays` (pruned once at startup; `0` keeps everything, default 365) — plus `vapidPrivateKeyFile`/`vapidPublicKey`/`vapidSubject` and `httpsCertFile`/`httpsKeyFile`/`httpsPort` for Web Push (see Push notifications below), and `updateApiKey` for `/update` auth (see the bullet below). Missing file/keys fall back to those defaults.
- **Sensor ingestion** — `POST /update`: when `webconfig.json`'s `updateApiKey` is set, requires a matching `X-API-Key` header (constant-time compared) and 401s otherwise; empty/missing `updateApiKey` (the default) leaves `/update` unauthenticated, unchanged from every prior version of this app. This matters once the fixed-backend-host override (see WiFi provisioning below) lets an ESP32 reach this backend from outside the LAN — an internet-reachable, unauthenticated `/update` would let anyone inject fake readings or spam the Sheets relay/push notifications; a same-LAN-only setup can safely leave it unset. Accepts either JSON body (`{temperature, turbidity, tdsVoltage, flowPulses}` from current firmware, or legacy `{temperature, turbidity, tds}` without `flowPulses`) or form-urlencoded body with `water_level`. Normalizes into a payload with `source`/`timestamp`, derives `ec` (electrical conductivity, µS/cm) from `tds` (`ppm_to_ec` — EC is not a separate sensor, it's the same DFRobot measurement before the standard EC→TDS ×0.5 conversion, so it always agrees with TDS), appends to the in-memory `history_buffer` for the live short-window graph, and broadcasts to all connected UI WebSocket clients as a `sensor_update` message. See Sensor calibration below for how `turbidity`/`tds`/`flowPulses` get calibrated before broadcast, and Flow sensor below for `flowPulses` specifically.
- **Dashboard fan-out** — `WS /ws/app`: browser dashboards connect here and receive `sensor_update` JSON messages. Connected clients are tracked in the `ui_clients` set guarded by `ui_clients_lock`; disconnects are pruned opportunistically during broadcast.
- **Backend discovery** — a UDP listener (`DiscoveryProtocol`, started via `@app.on_event("startup")`) binds `0.0.0.0:8888` and replies `HYDRO_HERE` to any `HYDRO_DISCOVER` packet, so firmware on the LAN can find this machine's current IP without it being hardcoded. Requires Windows Firewall to allow inbound UDP on port 8888 (added locally via `netsh advfirewall firewall add rule name="HydroMonitor UDP Discovery" dir=in action=allow protocol=UDP localport=8888` — a fresh machine won't have this rule and discovery will silently time out until it's added). This only ever finds a backend on the ESP32's own subnet, since UDP broadcast doesn't cross networks — see the fixed-backend override below (WiFi provisioning) for a backend on a different network.

## Sensor calibration (backend-owned)

Calibration lives on the backend, not the firmware, so sensors can be recalibrated live with **no reflash**. The firmware streams raw values; `main.py` converts them using coefficients persisted in `calibration.json` (path configurable via `webconfig.json`'s `calibrationFile`, default `calibration.json`; the file is git-ignored and created on first save). Missing/invalid file → sensible defaults (turbidity uncalibrated, TDS k-factor 1.0, flow k-factor 450.0 — the YF-S201 nominal).

- **Models**: turbidity is a **2-point linear** ADC→NTU map (`ntu = slope·adc + intercept`; slope is negative since higher ADC = clearer water; needs ≥2 captured points or it returns `None`/no NTU). TDS is the DFRobot temperature-compensated ppm polynomial (moved here from the firmware, using the live DS18B20 temp) scaled by a **single k-factor** fitted against one known-ppm solution. Flow uses the same single-k-factor shape as TDS (`k` = pulses per liter, YF-S201 nominal ≈450) fitted against one known-volume pour; unlike the other three params it has **no good/warn/danger thresholds** — it's a plain quantity, not a water-quality judgment, so it's absent from `thresholds.py`'s `RANGE_BANDS`/`PUSH_PARAMS`.
- **Calibration mode gate**: saved coefficients only apply when `calibration_mode` is ON (the `/calibrate` page's on/off toggle, `POST /calibration/mode`). OFF → `/update` always emits raw ADC (`turbidityUnit: "ADC"`) and uncalibrated DFRobot ppm (k=1.0), regardless of what's saved in `calibration.json` — so a saved-but-unverified calibration can't silently affect the live dashboards until explicitly switched on.
- **`/update` output**: emits both raw and calibrated fields. `turbidity` carries **calibrated NTU** once a calibration exists, else falls back to raw ADC — kept this way because the *original* React SPA that used to live at `/` was a prebuilt bundle we couldn't edit and hardcoded the "NTU" label on whatever `turbidity` contained (see Frontend below — that bundle is gone now, but the field shape stayed since the current frontend also just wants real NTU). `turbidityRaw` always carries the raw ADC (used by the calibration page and Google Sheets logging), `turbidityUnit` is `"NTU"`/`"ADC"` (the frontend reads it to label correctly), `turbidityNtu` is the calibrated NTU or `null`. TDS: `tdsVoltage` (raw) and `tds` (calibrated ppm).
- **Calibration page** — `GET /calibrate` serves `web/calibrate.html`, a self-contained standalone page (independent of the main frontend's own Calibration tab — see Frontend) that polls `GET /calibration` ~1s for live raw values, lets you enter a known reference + capture a point (the backend averages the last ~5 raw readings to reduce noise), shows the computed coefficients, and saves. Tracks an observed min/max of the live raw reading while turbidity is open (client-side only) with "use min"/"use max" buttons to fill the raw-ADC input, plus a "Reset range" button that only clears that local tracking, never the saved calibration.
- **REST API** (all under `/calibration*`, distinct from the `/calibrate` page): `GET /calibration` (state + `latestRaw`), `POST /calibration/mode` `{enabled}`, `POST /calibration/capture` `{sensor, reference, label?}`, `DELETE /calibration/point` `{sensor, index}`, `POST /calibration/save` (persists to `calibration.json`), `POST /calibration/reset` `{sensor}`. `sensor` is `"turbidity"`, `"tds"`, or `"flow"`. Captures/edits are in-memory until an explicit save.
- **Note**: Google Sheets logging is unchanged — it still logs raw ADC turbidity + (now backend-calibrated) TDS ppm; it does not log flow rate/usage at all (see the flow sensor's own note below). Adding NTU columns would require an Apps Script schema change.

## Flow sensor (water usage & current flow)

A fifth **main** sensor (not a water-quality param — see Sensor calibration above), added alongside temperature/turbidity/TDS/EC. A YF-S201 hall-effect flow sensor on the ESP32's GPIO27 (digital pulse input, not analog) reports a raw pulse count each `/update`; the backend converts it via the `"flow"` calibration k-factor into two facets:

- **Current flow rate** (`payload["flowRate"]`, L/min) — instantaneous, ephemeral like the other live params (broadcast over `/ws/app`, stored per-reading in `storage.py`'s `readings.flow_rate` column, no thresholds/push alerts).
- **Water usage** (`payload["waterUsageToday"]`, liters) — a **daily-resetting** cumulative counter, tracked in a separate `storage.py` table `daily_usage(date, total_liters)` keyed by local calendar date. A day rollover naturally starts a fresh row (no scheduler needed for the automatic daily reset); `POST /flow/reset-today` zeroes the current day's row on demand (manual reset). `GET /flow/usage?days=N` returns today's running total plus the last N days' totals, for the dashboard's "Water Usage" bar chart — a separate small endpoint from `/history`'s three-tier merge, since daily totals are a different shape/cadence (one row per day, kept indefinitely, not subject to `historyRetentionDays`) than the per-2s `readings` table.
- **Frontend**: `flow` is a `ParamKey` (shows in the ParamGrid, quick-view, Settings display toggles, Calibration tab) but is **absent from `RANGE_BANDS`/`ThresholdParam`** (`frontend/src/lib/thresholds.ts`) — every component that scores/colors a param guards against this (`ParamCard`'s optional `param` prop, `ParamDetailDialog`'s `rangeParam` narrowing, etc.), the same pattern already used for an uncalibrated/unscorable turbidity reading. Two dedicated charts on the main Dashboard (`WaterFlowChart.tsx`, `WaterUsageChart.tsx`) sit below the ParamGrid; both respect the Settings dialog's show/hide toggles (`DashboardPrefsProvider`, localStorage-persisted) and render nothing when hidden.
- **Not logged to Google Sheets** — `sheet_payload` in `update_sensor` doesn't include flow fields, so Sheets-sourced `/history` rows get `flowRate: null` via `_with_ntu`'s uniform backfill (matching how `ec` is backfilled for legacy Sheets rows lacking that column).

## Google Sheets logging & history (`google_apps_script.gs`)

- Every `/update` POST that includes `temperature`+`turbidity` is relayed fire-and-forget (via `asyncio.to_thread`, so a slow/unreachable Google endpoint never blocks the ESP32's `/update` response) to a Google Apps Script Web App, configured by `webconfig.json`'s `googleSheetsWebhookUrl`. If that key is empty/missing, the relay and `/history` both no-op.
- `google_apps_script.gs` is reference-only — it does not run from this repo. Paste it into the target spreadsheet's **Extensions > Apps Script** editor and deploy as a Web App (**Execute as: Me**, **Who has access: Anyone**).
- **`doPost` inserts each new reading at row 2** (right after the header), pushing everything else down — newest reading is always the top data row. This was changed from the original bottom-append model so recent data is always readable without scrolling; older rows appended under the previous model just sit further down and are never touched. Columns: `Timestamp, Temperature (C), Turbidity (raw ADC), TDS (ppm)`. Turbidity is logged as the same raw averaged ADC value shown on the dashboard — the NTU conversion (`adc_to_ntu` in `main.py`) is currently bypassed pending calibration, so no calibrated NTU value reaches the sheet.
- `doGet` accepts `?seconds=` and `?maxPoints=` (default 900s / 400 points), reads a **leading** slice of the sheet (rows 2..N — the newest readings, matching the insert-at-top write above), reverses it back to chronological ascending order, filters to the requested window, and stride-downsamples to at most `maxPoints` so long windows stay small and fast.
- **`GET /history?window=`** — dashboard-facing endpoint in `main.py`, selectable window (`5m`/`15m`/`1h`/`3h`/`12h`/`24h`, default `15m`, `HISTORY_WINDOWS`). **Three tiers, cheapest first**, merged into one chronological list; the response's `source` field reports which contributed (e.g. `db`, `db+sheet`, `live`):
  1. **local SQLite** (`storage.py`) — answers any window straight off disk and survives restarts, so it is preferred whenever enabled;
  2. **in-memory `history_buffer`** — only contributes rows newer than the DB's newest (a failed insert), or everything when the DB is disabled;
  3. **Google Sheets** — proxies `doGet` with matching `seconds`/`maxPoints` (keeping the dashboard's fetch same-origin, avoiding browser CORS/redirect issues with Google), consulted *only* for the part of the window local sources don't reach: a fresh DB, a restored machine, or readings predating the DB.

  The gap test allows `HISTORY_GAP_TOLERANCE_MS` (15s) of slack — readings arrive every 2s, so the first row at/after a cutoff is essentially always a second or two late, and testing for an exact match made every steady-state request look like a gap and fire a pointless multi-second Sheets round-trip. Every row gets `turbidityNtu` (calibrated from raw ADC via `_with_ntu`) and `ec` (from `tds` if not already present) added uniformly across all three sources.
- **Local history database** (`storage.py`, `historyDbFile`) — every `/update` reading is written to SQLite (WAL, `synchronous=NORMAL`) via `asyncio.to_thread`, fire-and-forget like the Sheets relay, so disk latency never delays the ESP32's response. Column names deliberately mirror `history_buffer` and the Apps Script's `doGet` (`timestamp` in epoch **milliseconds**, `turbidity` = raw ADC) so rows from all three sources merge without translation. Failures here are never fatal — a bad path or permission error just logs and degrades to the previous buffer + Sheets behavior. The file is git-ignored (site measurement data, not code); back it up separately.
- **Redeploy gotcha**: after editing `doGet`/`doPost` in the Apps Script editor, redeploy the web app as a **new version** — otherwise `/exec` keeps serving the old code and `GET` silently returns nothing. The insert-at-top change described above lives only in this repo's reference copy until you do this; the currently-deployed script keeps appending at the bottom (still fully correct for `/history`, just not "newest at the top" if you open the sheet by hand) until redeployed.
- Running min/max per sensor (`temperature`/`turbidity`/`tds`) is tracked separately in `main.py`'s in-memory `sensor_stats` (since server start, resets on restart, shared across all connected dashboards) — it is not persisted to or read from the spreadsheet.

## Push notifications (Web Push)

Threshold-breach alerts delivered as OS-level push notifications, so a subscribed browser gets warned even when the dashboard tab isn't open. Independent of the in-app WQI/ParamGrid coloring — this is an *outbound* notification path on top of the same `range_status_for` scoring `/update` already does.

- **VAPID keys**: `webconfig.json`'s `vapidPrivateKeyFile` (default `vapid_private_key.pem`, git-ignored — generate your own with `vapid --gen` from `py-vapid`, pulled in by `pywebpush`), `vapidPublicKey`, `vapidSubject` (a `mailto:` contact required by the Push protocol). `vapid_available()` checks the private-key file exists and the public key is non-empty; every `/push/*` endpoint 503s rather than crashing startup if VAPID isn't configured.
- **HTTPS listener**: Web Push requires a secure context, and `http://localhost` is only exempt on the *same machine* — a phone/other device on the LAN needs real HTTPS. `webconfig.json`'s `httpsCertFile`/`httpsKeyFile` (both empty by default — HTTPS stays off) and `httpsPort` (default 8443) start a **second** uvicorn `Server` instance alongside the always-on HTTP:8080 one, both serving the same FastAPI `app`. Since FastAPI's `@app.on_event("startup")` fires once per `Server`, a module-level `_discovery_listener_started` guard keeps the UDP discovery listener from trying to bind port 8888 twice (which would crash the second server's startup). A self-signed cert works for LAN testing but needs its CA trusted per-device (Android in particular refuses to register a Service Worker over an untrusted cert even after "proceed anyway"); a public tunnel (e.g. `cloudflared tunnel --url`) or a private-mesh solution (e.g. Tailscale + `tailscale cert`) sidesteps that for real testing.
- **Subscription storage** (`storage.py`'s `push_subscriptions` table) — one row per browser push endpoint (not per-user; there's no user/account concept anywhere in this app), holding the endpoint URL, the `p256dh`/`auth` keys from the Push API, and a `prefs_json` blob (`{param: {warn: bool, danger: bool}}`, default warn=off/danger=on for `temperature`/`turbidity`/`tds`/`ec` — **not** `flow`, which has no thresholds to breach).
- **Trigger**: `_check_breaches_and_dispatch` runs inline on every `/update` (must observe every reading in order to edge-detect correctly), comparing each param's status against `last_severity` — a push only fires on the **good→warn/danger transition**, not on every reading while still breached (re-arms once the reading recovers to good). The actual sends are deferred via `asyncio.create_task`, the same fire-and-forget pattern as the Sheets relay and local DB insert, so a slow/unreachable push service never delays the ESP32's `/update` response.
- **Payload**: `PARAM_DISPLAY` (emoji/label/unit per param, hand-mirrored from `frontend/src/lib/paramMeta.ts` same as `thresholds.py` mirrors `RANGE_BANDS`) builds a rich title/body (e.g. `"🌡️ Temperature — Warn"` / `"33.1 °C is in the warn range"`), plus an `icon`/`badge` (the app favicon) and two action buttons (`view` → opens the dashboard, `dismiss` → closes only) — all consumed by the service worker below. A dead subscription (push service returns 404/410) self-heals by deleting that row.
- **REST API**: `GET /push/vapid-public-key`, `POST /push/subscribe` `{endpoint, keys:{p256dh,auth}, prefs?}`, `POST /push/unsubscribe` `{endpoint}`, `GET /push/preferences?endpoint=`, `PUT /push/preferences` `{endpoint, prefs}`, `POST /push/test` `{endpoint}` (sends one real push immediately, bypassing prefs/thresholds — backs the Settings dialog's "Send test notification" button so a user can see what the popup looks like without waiting for a real breach). All 503 if local SQLite storage is disabled (subscriptions have nowhere durable to live otherwise).
- **Frontend**: `frontend/src/lib/push.ts` is the browser-side plumbing (Service Worker registration, subscribe/unsubscribe, prefs get/save, `sendTestPush`); `frontend/public/sw.js` is a **plain vanilla JS** file (not run through Vite's build — no imports/exports/TypeScript) handling the `push` and `notificationclick` events. The UI lives in the **Settings** dialog (see Frontend below), not a standalone bell icon — that was an earlier iteration, folded in once a general Settings surface was added.

## WiFi provisioning over USB (`wifi_serial.py`)

Lets the dashboard change the ESP32's WiFi network the way an OS WiFi picker does — scan, pick a network, type a password, connect — with the new credentials persisted on the device (NVS flash, survives power cycles and re-flashing the sketch). A **separate channel** from every other feature in this app: at the moment credentials need to change, the ESP32 may have no working WiFi at all, so the dashboard (normally reached over HTTP/WiFi) can't get to it that way. The only path available is the **USB cable itself** — `main.py` (on the PC the board is plugged into) talks directly to the ESP32's USB-serial port, bypassing WiFi/HTTP entirely for this one feature.

- **Firmware side** (`firmware/esp32/esp32.ino`): a line-based serial protocol, every machine-readable line prefixed `WIFI_`/`BACKEND_` so it can't collide with the sketch's existing free-form `Serial.println` debug output. `WIFI_SCAN` → `WiFi.scanNetworks()`, prints `WIFI_NET|<ssid>|<rssi>|<encrypted:0|1>` per result then `WIFI_SCAN_DONE`. `WIFI_SET|<ssid>|<password>` → attempts to connect **without saving first**; only on confirmed `WL_CONNECTED` does it persist to NVS (`Preferences`, namespace `"wifi"`) and reply `WIFI_CONNECTED|<ip>` — a bad password never overwrites a working saved network, and the board falls back to reconnecting with whatever was working before. `WIFI_STATUS` reports current connection state. Commands are read non-blockingly (`readSerialCommands()`, called every `loop()` iteration and during `setup()`'s WiFi-connect wait) so the board stays reconfigurable over USB at any time — including immediately at boot if the stored credentials turn out to be wrong, rather than requiring a re-flash to recover. `setup()`'s initial WiFi-connect wait is **bounded** (20s, not infinite) for the same reason.
- **Fixed backend host override (different network from the backend PC)**: same-LAN UDP discovery (see Backend discovery above) can only ever find a backend sharing the ESP32's subnet — it cannot help when the board and the backend PC are on different WiFi networks. `BACKEND_SET|<host>|<apiKey>|<https:0|1>` persists a hostname/IP (plus, optionally, an API key and an HTTPS flag) to NVS (`Preferences`, namespace `"backend"`, separate from WiFi creds) and immediately switches the board to POSTing straight to that host, skipping discovery entirely — the failure-triggered "3 failed POSTs → rediscover" path also just re-applies the fixed host instead of re-broadcasting. `apiKey`, when set, is sent as the `X-API-Key` header on every `/update` POST and should match the backend's `webconfig.json` `updateApiKey` (see Config above); `https`, when on, POSTs to `https://<host>:8443/update` (the `httpsBackendPort` const, matching `webconfig.json`'s default `httpsPort`) via `WiFiClientSecure` with `setInsecure()` (no CA store on the board, so it encrypts the payload/API key in transit but doesn't validate the server's cert — accepted tradeoff for a hobby monitor, not a security-critical deployment) instead of plain `HTTPClient`. `BACKEND_CLEAR` erases the override (host, key, and HTTPS flag) and reverts to same-LAN auto-discovery. `BACKEND_STATUS` reports `<fixed:0|1>|<host>|<current backendUrl>|<hasApiKey:0|1>|<https:0|1>` — the key itself is never echoed back over serial, same as the WiFi password never is. `BACKEND_TEST` has the board itself `GET` `main.py`'s `GET /update/health` (a no-op auth/reachability check, factored out of `/update`'s own auth so it doesn't write a fake sensor reading) against whatever `backendUrl` is currently in effect, through the board's *own* WiFi/DNS/TLS stack -- this is what makes it a meaningful test: a check run from the backend machine itself can't tell you whether the board's own network path (its router's NAT/port-forward, its DNS resolution of a DDNS name, its TLS handshake) actually works. Reports `BACKEND_TEST_OK|<httpCode>` for any HTTP response at all (even a 401 -- that's "reachable, but check the API key") or `BACKEND_TEST_FAILED|<reason>` for a connection-level failure (DNS/TCP/TLS, WiFi not connected, or nothing configured yet). **The board only needs to know the address — the backend PC still has to actually be reachable from the board's network** (port-forward + dynamic DNS, a VPN/mesh network like Tailscale, or a tunnel), which this feature doesn't set up by itself; setting an `apiKey` (and turning `https` on, so it isn't sent in cleartext) is what keeps that newly-internet-reachable `/update` from accepting forged readings from anyone else who finds it.
- **Backend side** (`wifi_serial.py`, mirrors `storage.py`'s structure: one module-level connection guarded by a lock, blocking calls, called via `asyncio.to_thread`): `find_port()` auto-detects the ESP32 by its USB-to-serial chip's VID:PID (CP2102, CH340/CH9102 — covers most ESP32 dev boards), overridable via `webconfig.json`'s `esp32SerialPort` if auto-detect ever picks the wrong device. Opening a fresh connection resets most ESP32 boards (DTR/RTS toggle, the same mechanism `esptool` relies on for flashing), so the first call after backend startup pays a ~2s settle delay; the connection is then reused across calls. Every function degrades to `{"ok": False, "error": ...}` rather than raising — an unplugged board is an expected, not exceptional, state. `set_backend_host(host, api_key, use_https)`/`get_backend_status()` mirror `set_wifi()`/`get_status()` for the `BACKEND_*` commands above.
- **REST API**: `GET /wifi/status`, `POST /wifi/scan`, `POST /wifi/connect` `{ssid, password}`, `GET /wifi/backend`, `POST /wifi/backend` `{host, apiKey, useHttps}` (empty `host` clears the override), `POST /wifi/backend/test` (no body -- triggers `BACKEND_TEST` above, returns `{reachable, httpCode, detail}`) — all 503 with a clear reason when the ESP32 isn't found on USB. Like every other endpoint in this app, unauthenticated (no login system exists anywhere in this codebase) — not a gap this feature introduces, but worth naming since these are the endpoints that accept a WiFi password / API key for the board to use.
- **Frontend**: a `"WiFi"` entry in the Calibration tab's `SensorList` (`WifiPanel.tsx`) — not an actual calibratable sensor (no `/calibration` coefficients), listed there because that's the natural home for "device setup" alongside the other per-sensor panels. OS-picker style: scan → strongest-signal-first list with a lock icon for secured networks → password field (skipped for open networks) → Connect, with a ~20s-tolerant loading state matching `WIFI_SET`'s connect timeout. A second card below it, "Backend on a different network," shows whether a fixed host is active (plus HTTPS/API-key-set indicators) and lets you set (host + optional API key + HTTPS toggle, on by default) or clear one, plus a **Test connection** button (enabled only once a fixed host is set) that calls `/wifi/backend/test` and toasts the result -- reachable-with-a-non-2xx (e.g. wrong API key) and unreachable (DNS/TCP/TLS/no-WiFi) are reported as distinct failure toasts, not lumped together.

## Frontend

**One dashboard**, source-controlled, served at `/` by `main.py` (the built `frontend/dist/`, mounted last as a root catch-all — see `main.py`'s bottom `app.mount("/", ...)`, registered after every API route so it only handles requests nothing more specific already matched). Full design/build history is in **`AQUA_MONITOR_PLAN.md`** and **`HANDOFF.md`**; this section is the short version.

- **Stack**: Vite + React 19 + TypeScript + Tailwind v4, shadcn/ui + Recharts + Motion + TanStack Query. Build with `cd frontend && npm install && npm run build` (outputs `frontend/dist/`, git-ignored along with `node_modules/`); `/` 404s until this has been built at least once. `npm run dev` runs a Vite dev server that proxies `/ws/app`, `/history`, `/calibration*`, `/update`, `/push*`, `/flow*`, `/wifi*` to `:8080` for HMR against a live `python main.py`.

## Firmware (`firmware/esp32/esp32.ino`)

Single ESP32 dev board (not ESP32-CAM — no camera). WiFi credentials are provisioned over USB and persisted to NVS flash (see WiFi provisioning above) — the hardcoded `defaultSsid`/`defaultPassword` consts are only ever used on a completely fresh, never-provisioned board. Not auto-synced with `main.py`; changing an endpoint contract there requires a matching firmware update.

Reads DS18B20 temperature, analog turbidity, TDS, and flow-sensor pulses every 2s and POSTs JSON `{temperature, turbidity, tdsVoltage, flowPulses}` to `http://<backendIP>:8080/update` — **all raw**: `turbidity` is the averaged raw ADC, `tdsVoltage` is the raw TDS sensor voltage, and `flowPulses` is the pulse count accumulated over that ~2s interval (via `attachInterrupt`, unlike the other three sensors' synchronous `analogRead` — pulses can arrive at any time, not just when polled). The DFRobot TDS ppm formula, its temperature compensation, turbidity NTU conversion, and the flow pulses→liters k-factor all live on the **backend** (see Sensor calibration below), so the firmware no longer computes any of them — this lets sensors be recalibrated live without reflashing. (Older firmware that POSTs a pre-computed `tds` ppm, or omits `flowPulses` entirely, still works: the backend passes a legacy `tds` through unchanged, and a missing `flowPulses` just means no flow reading for that update.) The backend IP is not hardcoded: `discoverBackend()` broadcasts `HYDRO_DISCOVER` over UDP on port 8888 and takes the replying host's IP as the backend address, so it survives the backend PC's DHCP lease changing. Discovery runs once at boot (blocking retry loop, **bounded to 20s** -- same reasoning as the WiFi-connect wait: a backend might never answer at all, e.g. running Google Sheets-fallback-only with no `main.py` anywhere, and an unbounded wait here would hang `setup()` forever, keeping `loop()` -- and therefore every sensor read and the Sheets fallback -- from ever running) and again automatically if `/update` POSTs fail 3 times in a row (`consecutiveFailures` / `backendKnown`), so a mid-run IP change self-heals within a few broadcast cycles, and a backend that shows up after boot is still picked up (`loop()` keeps retrying discovery on its own timer once per `broadcastInterval` tick while `backendKnown` is false). Requires `main.py`'s discovery listener (see above) and a working Wi-Fi broadcast domain. Registers mDNS as `hydromonitor.local` but doesn't actually use that hostname anywhere — that's unrelated leftover, not part of backend discovery.

**Google Sheets fallback (no backend needed)**: when the backend is unreachable (never discovered, or the most recent POST just failed) but Wi-Fi/internet still work, readings aren't silently dropped -- they're pushed into a 30-entry circular buffer (`sheetsFallbackBufferPush`, one push per `broadcastInterval` tick, ~60s worth at the normal 2s cadence) and, once per `sheetsFallbackInterval` (60s), the board flushes the whole buffer by POSTing each buffered reading **individually, straight to the same Google Apps Script Web App** `main.py`'s own Sheets relay uses (`google_apps_script.gs`'s `doPost`) — no third-party service, no separate account, and it lands in the identical sheet/row shape a normal backend-relayed reading would (`doPost` doesn't distinguish the two; see `google_apps_script.gs`'s header comment). A buffer overflow (the 60s window arrives late) drops the oldest reading, not the newest. The buffer is cleared both after a flush attempt and the moment the backend POST succeeds again (stale readings from before recovery aren't worth re-sending once the backend itself is caught up). Requires pasting the deployed Apps Script `/exec` URL into `sheetsWebhookUrl` (must be the same URL/spreadsheet as `webconfig.json`'s `googleSheetsWebhookUrl`, so both paths write to one sheet). **Caveat**: the firmware has no access to the backend's `calibration.json`, so a fallback reading's `tds` field is the sensor's raw voltage, not calibrated ppm — same as `turbidity` already always being raw ADC regardless of source. Flow (`flowPulses`) is **not** included in this fallback or in the buffer -- only temperature/turbidity/TDS, matching what `doPost` accepts.

### Wiring

The turbidity NTU formula (`-1120.4·V² + 5742.3·V - 4353.8`) is calibrated for a 5V-powered analog turbidity sensor with a ~0–4.5V output range (DFRobot Gravity-style). ESP32 GPIOs are strictly 3.3V (not 5V-tolerant like some ESP8266 boards), so the sensor's output is scaled down through a voltage divider before reaching the ADC pin, and the firmware scales it back up (`dividerRecoveryFactor`) before applying the NTU formula.

| Sensor | Pin | ESP32 pin | Notes |
|---|---|---|---|
| DS18B20 (temp) | VCC | 3.3V | Keeps the OneWire data line's HIGH level at a safe 3.3V |
| | GND | GND | |
| | DATA | GPIO13 | Needs a 4.7kΩ pull-up to 3.3V (skip if the probe already has one). **Not GPIO12** — that's a boot-strapping pin (sets flash voltage); the required pull-up would hold it HIGH at reset and can prevent the board booting at all |
| Turbidity sensor | VCC | 5V / VIN | Needs 5V to hit its rated output curve — must be a true 5V rail |
| | GND | GND (shared) | |
| | OUT | → divider → GPIO34 | GPIO34 is ADC1 (input-only, no internal pulls); avoid ADC2 pins (0,2,12–15,25–27) since Wi-Fi disables ADC2 |
| TDS Meter V1.0 | VCC | 3.3V | Accepts 3.3–5.5V; output voltage is independent of supply choice |
| | GND | GND (shared) | |
| | A (signal) | GPIO35 (direct, no divider) | Output tops out at ~2.3V, safely under the 3.3V ADC limit. Another ADC1 pin, kept separate from GPIO34/GPIO13 |
| YF-S201 (flow) | VCC | 5V / VIN | Hall-effect sensor needs 5V to hit its rated output |
| | GND | GND (shared) | |
| | Signal | GPIO27 (direct, `INPUT_PULLUP`) | **Digital** pulse input, not analog — the "avoid ADC2 pins" note above is about `analogRead` reliability under Wi-Fi and doesn't apply to a plain digital interrupt pin, so GPIO27 (an ADC2 pin) is fine here despite being in that avoid-list for analog use. Open-collector output, needs a pull-up (the ESP32's internal one via `INPUT_PULLUP` is sufficient) |

Divider (turbidity only): R1 = 10kΩ (sensor OUT → node), R2 = 20kΩ (node → GND), node → GPIO34. Scales 0–4.5V down to 0–3.0V (safe margin under the 3.3V ADC limit); firmware multiplies by 1.5 (`dividerRecoveryFactor`) to recover the sensor's real voltage. Re-verify the NTU calibration against known reference samples once wired — the formula was tuned for the original ESP8266 read path, not this divider, and ESP32's ADC has known non-linearity near its extremes.

TDS reading uses DFRobot's official temperature-compensated formula, reusing the DS18B20's `temperatureC` (compensation coefficient `1 + 0.02·(T-25)`) rather than assuming a fixed 25°C, since the sensor's raw output drifts with water temperature.

Flow sensor uses `attachInterrupt(digitalPinToInterrupt(FLOW_PIN), onFlowPulse, RISING)` with a `volatile` pulse counter guarded by `portENTER_CRITICAL`/`portEXIT_CRITICAL` (a `portMUX_TYPE`, not just `noInterrupts()`/`interrupts()` — ESP32 is dual-core, so a simple interrupt-disable doesn't protect against the other core) — the only interrupt-driven sensor in this firmware, everything else is synchronous `analogRead` polled once per `broadcastInterval` tick. The counter is snapshotted and reset to 0 each tick so `flowPulses` always represents "pulses since the last POST," matching how turbidity's 20-sample average is scoped to one tick.
